## Release conclusion

The exposed `create_deployment` MCP schema has **no supported per-deployment staging flag**. `target: "production"` must not be treated as “build production without moving domains.” Do not pass undeclared `autoAssignCustomDomains`, `alias`, or `skipDomain` keys to that tool. There is a supported **project setting** alternative, `update_project.requestBody.autoAssignCustomDomains: false`, which changes project-wide behavior. The operator must record the original setting, verify it before creating the production build, and inspect its value again after promotion.

Recommended coordination sequence, as an operator procedure rather than evidence of actions performed:

1. Retain the currently serving deployment ID and domain mappings as rollback evidence. Pin the candidate to the final reviewed source SHA, preserving existing Preview and patch history.
2. Finish rendered review and relevant build/content checks on a candidate Preview. Remove the preview-only review harness from the production candidate; inspect the source diff and make sure removal does not alter public CSS or content.
3. If using project-level staging, record the original auto-assignment setting and confirm that no concurrent release is changing it. Set only the supported field to `false` and read it back. Create the production candidate from the pinned SHA, poll readiness/logs, and verify that live domain mappings still serve the previous deployment.
4. Validate the production candidate's public HTML, downloads, images, security headers, canonical URLs, and source identity before `request_promote`. Then inspect promotion/alias results and request both public hosts directly.
5. Inspect the project's auto-assignment setting again, restore the prior intended value where necessary, and record the resulting value. Do not assume promotion leaves it unchanged. A previously promoted deployment should use the documented rollback workflow, not repeated promotion.

If project-level staging is inappropriate because of a concurrent release, a fully reviewed Preview followed by a fresh production build is possible within explicit user authorization. Record honestly that public cutover then occurs at build completion; verify the exact production source and aliases immediately and retain rollback evidence. This is an operational choice, not a hidden stage flag.

## Same-origin responsive harness

A temporary same-origin page containing an iframe at 360, 390, and 430 CSS pixels can produce real narrow-layout rendering of the app in the available desktop browser. Its result should be labelled **responsive mobile viewport review in desktop Chromium**, not real-device mobile, Safari, touch, or device emulation. Prefer additionally checking 320 CSS pixels if claiming WCAG Reflow coverage.

| Concern | Evidence and practical implication | Source | Label |
|---|---|---|---|
| Width-based responsive rules | Width/height media queries inside an iframe use that iframe's viewport. Its `vw`/`vh` are relative to the nested viewport, so a narrow iframe tests responsive CSS rather than merely shrinking a screenshot. Record actual inner width and height, because scrollbars can affect the usable width. | [MDN viewport concepts](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/CSSOM_view/Viewport_concepts) | Platform documentation / measurement recommendation |
| `X-Frame-Options: SAMEORIGIN` | Embedding requires all ancestor frames to have the same origin as the framed page. Use a relative iframe source on the exact candidate hostname, keeping security headers intact. Check CSP `frame-ancestors` independently if present. | [MDN X-Frame-Options](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/X-Frame-Options) | Platform documentation |
| Mobile layout versus visual viewport | Only the top-level window has a visual viewport distinct from its layout viewport; iframe metrics correspond to the layout viewport. Phone virtual keyboards and pinch zoom can reduce the visible area separately. A fixed-height iframe cannot certify those behaviors or browser-chrome changes. | [MDN VisualViewport](https://developer.mozilla.org/en-US/docs/Web/API/VisualViewport) | Platform documentation / test limitation |
| Touch and pointer rules | `pointer` reports the accuracy of the primary input mechanism. Setting iframe width does not turn a desktop mouse into a coarse touchscreen. Click testing confirms functional controls in that environment, not gesture or touch behavior. | [MDN pointer media feature](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@media/pointer) | Platform documentation / test limitation |
| Pixel density | `devicePixelRatio` describes physical-to-CSS pixel density for the actual display. An iframe width alone does not reproduce phone density or every responsive image selection condition. | [MDN devicePixelRatio](https://developer.mozilla.org/en-US/docs/Web/API/Window/devicePixelRatio) | Platform documentation / test limitation |
| Reflow and tables | WCAG Reflow uses 320 CSS pixels for ordinary vertically read content. Data tables may need two-dimensional layout; their exception does not extend to headings or adjacent paragraphs. An independently scrollable table is different from unreadable page-wide text overflow. The proposed 360/390/430 checks alone do not establish WCAG conformance. | [W3C Understanding Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html) | Standards owner guidance / scope limit |

Review the complete public route census in the actual iframe, including lower-page text, every image and caption, table scrollability, sticky header obstruction, article anchors, menu opening/closing, cookie choices, filter states, FAQ details, links and downloads. Keep a route × viewport ledger with exact candidate SHA, observed viewport, pass/fail evidence, and explicit exceptions. A DOM overflow measurement is useful but cannot replace viewing cropping, line wrapping, obscured elements, and all page sections. Candidate changes after the review require checking the changed behavior again. Remove the harness before the final production commit and verify its route is absent after deployment.

This method does not need raw CDP, private Cua methods, browser state manipulation, or another browser automation stack. It does not prove Android/iOS browser compatibility or touch-device behavior; those require an authorized actual mobile-capable surface or separately supplied device evidence.
